# Security and robustness audit: October 2026

**Scope.** The backend as pushed to `main` at commit `15fddbc` (phases 0 to 3b), plus the frontend's dependencies,
the Dockerfile and the CI workflow. All GitHub Actions runs up to that commit are green.

**Method.** A read-through of the request path (socket loop, message reader, upload assembler, dataset
factory, text import, session manager, execution gate, rehydrate), targeted searches of the domain code
(input-sized allocations, recursion, broad `catch`), `npm audit`, and a review of the container and CI files.

**Not done (yet).** Load and memory measurements, fuzzing, a container image scan, and a runtime review of the
frontend. Numbers below marked *estimate* are arithmetic from the data structures, not measurements.

**Threat model.** A public WebSocket service with no accounts. Everything a client sends is hostile. There is no
database, no secret and no personal data at rest, so the realistic goals of an attacker are to crash the process,
exhaust memory or CPU, starve other users, or make one user's request misbehave. Availability is the main concern.

Severity: **High** = one client can take the whole server down. **Medium** = degrades service or hides bugs.
**Low** = hygiene.

## Findings

| ID | Sev | Finding | Fix | Status |
| --- | --- | --- | --- | --- |
| H1 | High | **No memory budget across sessions.** `MaxSessions` counts sessions, not size. A 2.5M-edge graph is about 30 MB, so 100 of them are about 3 GB (*estimate*). A single operation on one also copies the edge list several times, roughly 100-200 MB transient (*estimate*). One process-wide OOM kills every user's session. | A dataset-weight budget summed over all sessions (create/rehydrate refused with `server-busy` beyond it); a container memory limit plus `DOTNET_GCHeapHardLimit`; measure real peaks with BenchmarkDotNet. | Open |
| H2 | High | **Text import allocates per line before checking limits.** `TextImport.Tokenize` splits a whole line into a string array. One 60 MB line of `0 0 0 ...` becomes about 30M strings (*estimate*: more than 1 GB) before the cell-count check runs. | Tokenise lazily over spans and stop at the limit; cap line length. | Open |
| H3 | High | **Upload amplification is not counted.** `MaxInFlightUploadBytes` counts buffered text, but parsing a 64 MiB array-style payload builds a `JsonDocument` at several times that size, plus the UTF-16 string copy. The text-import path is cheap (a string is one JSON token); the array path is not. | Count a parse-cost multiplier in `UploadBudget`, lower `MaxUploadBytes` to what the limits really need, prefer text import for large graphs. | Open |
| M1 | Med | **Idle and slow connections are never closed.** Only an in-progress upload has a read timeout. A client can open a connection and send nothing, or send half a message and stall, holding one of its 10 per-address slots indefinitely. No WebSocket `KeepAliveTimeout`, so half-open connections linger. | Idle timeout (no session and no traffic), per-message completion timeout, `KeepAliveTimeout`. | Open |
| M2 | Med | **Dataset construction is outside the execution gate.** `DatasetFactory.Create` (a JSON graph of 2.5M edges, a text import, `Tree.FromValues`) runs before `ExecutionPolicy` and with no time limit, so many connections can saturate the thread pool and CPU. | Build datasets under the gate with an `OperationContext`. | Open |
| M3 | Med | **No access control and a small shared pool.** Anyone can open sessions; 10 addresses fill the 100-session capacity. Acceptable for a demo, a decision for anything else. | Decide: accept, add an optional access token (`Security:AccessToken`), or a join code for the demo. | Decision needed |
| M4 | Med | **Execution slots are not shared fairly.** One address with 10 connections can occupy every execution slot (default: one per CPU core), so others get `server-busy`. | Cap concurrent operations per address (for example half the slots). | Open |
| M5 | Med | **Input errors are classified by exception type.** `InvalidOperationException`, `KeyNotFoundException`, `FormatException` and `ArgumentException` are all reported to the client as "invalid options" and not logged. A real bug that throws one of them (a LINQ `Sequence contains no elements`, say) is hidden and leaks a framework message. | A dedicated `InvalidOptionsException` and a shared option reader; log everything else as a bug. | Open |
| M6 | Med | **Unknown option keys are silently ignored.** `{"quarterTurn": 2}` (typo) runs `rotate` with the default. A mistyped `directed` flag does the undirected thing without a word. | Parse options through the descriptors and reject unknown keys, wrong types and missing required options in one place. | Open |
| L1 | Low | CI workflow has no `permissions:` block and uses action tags (`@v4`), not commit SHAs. | `permissions: contents: read`; pin by SHA via Dependabot. | Open |
| L2 | Low | No Dependabot for NuGet, npm, GitHub Actions or Docker. Docker base images use a floating `9.0` tag. | Add `.github/dependabot.yml`; pin image digests. | Open |
| L3 | Low | `Microsoft.AspNetCore.OpenApi` is referenced but unused. | Remove, or use it. | Open |
| L4 | Low | `npm audit`: 2 moderate findings, both via `@tailwindcss/typography` to `postcss-selector-parser`. Build-time only, not shipped. | Update when a fixed typography release is available. | Open |
| L5 | Low | HTTP responses carry no `X-Content-Type-Options: nosniff`. Endpoints are JSON only, so the impact is small. | Add the header. | Open |
| L6 | Low | Refused connections log the client IP. Under GDPR an IP address is personal data. Fine for security logging; worth a line in the privacy notes if this ever runs publicly. | Document retention. | Open |

## Checked and found sound

- **Per-operation limits.** A deterministic work budget (200M units) plus a wall-clock limit, cooperative via
  `Checkpoint`; a catalog-wide contract test fails any operation that never consults its budget. Aborted
  operations commit nothing (copy-on-write plus commit after `Execute`).
- **Hostile option values.** A contract test feeds every operation 12 hostile values per option (negative, huge,
  wrong type, null) and allows only the client-input exceptions.
- **Stack depth.** A search for self-recursive methods found only `RemoveNodeOperation.RemoveAt`, which is bounded by
  design to one extra step. Graph and tree traversals are iterative. JSON nesting is capped by System.Text.Json (64).
- **Allocation guards.** The input-sized allocations in the domain code (`all-pairs` n×n, `graph-to-matrix`, mazes,
  visited arrays) are guarded by `DatasetLimits` or an explicit node cap before allocating.
- **Messages and uploads.** Per-frame limit checked as frames arrive; chunked uploads have out-of-order, size,
  count, timeout and global-budget checks, and release their bytes on every exit path.
- **Rehydrate.** The whole operation log shares one context, so a long history cannot buy unlimited work; a failed
  rehydrate leaves the old session intact.
- **Concurrency.** One lock per session, always taken alone (no lock ordering to get wrong); the idle sweeper only
  uses `TryEnter`; the execution slot is released before any socket write.
- **Browser access.** Origin check on the WebSocket, CORS for `GET`, per-address connection cap, duplicate request ids.
- **Container.** Multi-stage, non-root, no secrets in the image; CI builds it and checks `/health`.
- **Build discipline.** `TreatWarningsAsErrors` is on; no WebSocket compression is enabled (no compression-oracle
  or zip-bomb surface).

## Edge-case coverage: the real gap

The contract tests run each operation against **one** sample dataset per type (a 6×8 matrix, an 8-node graph,
a 7-node tree). Operations are not exercised on the inputs where bugs usually live. The plan in
[ROADMAP.md](ROADMAP.md) (phase 4) adds an operations × adversarial-datasets matrix:

- Graphs: 0 nodes, 1 node, a self-loop, parallel edges, two components, negative weights, a negative cycle, a
  directed chain of 100,000 nodes, a star, a complete graph at the all-pairs limit, duplicate weights (ties).
- Matrices: 1×1, 1×N, N×1, all zeros, all equal, negative values, `int.MaxValue` values (overflow), the largest
  allowed size.
- Trees: empty, one node, a 100,000-node chain (degenerate), duplicates, after many removals (dead slots).

The assertion for every combination: the operation either succeeds or fails with the documented client-input
exception, never with `NullReferenceException`, `IndexOutOfRangeException`, `DivideByZeroException`,
`OverflowException` or an `OutOfMemoryException`; it never mutates its input; it is deterministic; and it respects
its budget.

## File-structure review

- `Engine.Domain/Operations/` is one flat folder of 46 files. Some hold one operation, some four or five
  (`GraphStructureOperations.cs`). At about 110 operations that is hard to navigate. Proposal: subfolders `Matrix/`,
  `Graph/`, `Tree/` (namespaces unchanged, so no churn elsewhere) and one file per operation from now on.
- Each operation is described in **three** hand-kept tables keyed by id (`OperationCatalog`, `OperationExamples`,
  `OperationDescriptors`), plus the test list in `OperationCatalogTests` and a count assertion. Contract tests keep
  them consistent, but adding 50 operations means touching four places each. Proposal: one definition per
  operation that carries id, label, category, description, options, example, result description and factory
  (explicit registration, no reflection), with option parsing driven by the declared options (fixes M5 and M6).
- `SessionSocketLoop.cs` (413 lines) holds the loop and every handler. Split into one handler per message once the
  hardening changes land.
- `Engine.Protocol.Tests` has 2 tests; the wire format is covered mostly by the gateway tests. Acceptable, but a
  golden-JSON test per message type would pin the contract the frontend depends on.
